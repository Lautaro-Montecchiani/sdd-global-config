Propose a new change - create the change and generate all artifacts in one step.

I'll create a change with artifacts:
- proposal.md (what & why)
- specs (requirements, delta format)
- design.md (how, including `## Security Layer`)
- tasks.md (implementation steps)

When ready to implement, the Agent runs `/openspec-apply-change <name>` (Antigravity) or `/opsx-apply <name>` (Cursor). Claude does NOT implement.

---

**Input**: The user's request should include a change name (kebab-case) OR a description of what they want to build.

**Steps**

0. **Read context (before starting)**

   Resolve vault and project name:
   ```powershell
   $vault = $env:OBSIDIAN_VAULT
   $p = Split-Path (Get-Location) -Leaf
   ```

   Read `$vault\projects\$p\context.md` if it exists and use it to inform the proposal — prior decisions, active changes, domain knowledge. If it doesn't exist, proceed without it. Read `$vault\projects\$p\arquitectura.md` and `docs/arquitectura/vision.md` if they exist to understand current architecture level, quality attributes, existing ADRs, components, and prioritized technical debt.

   **Complete `openspec/config.yaml` if needed** (edit only what is missing; keep `schema`, `rules`, other keys and comments intact):
   - If the file does not exist (e.g. after `openspec init` in OpenSpec 1.4.1): create it with `schema: spec-driven`.
   - If it has no `project_type`: ask for it (`frontend`, `backend-api`, `etl`, `scripts`, `fullstack`, `tooling`, `config`) and add it. If the user does not know, infer it from the repo, write it with the comment `# inferido — revisar` on the same line, and mention it in the final summary.
   - If it has no active `context:` (missing, or only commented out as in the file generated by `openspec init` in 1.14.x): add `context: |` with one line describing the project.
   - If `project_type`, `## Tests`, or `## Arquitectura` are missing, ask for them in the SAME question.

   Read `project_type` from `openspec/config.yaml` and apply the minimum security controls for that type (see the global CLAUDE.md). `design.md` MUST include a `## Security Layer` section.
   Read the `## Tests` subsection from the `context:` in `openspec/config.yaml`. If it does not exist, ask the user for it ONCE (keys: `comando`, `comando-rapido`, `timeout` in minutes, `entorno`, `excluir`; use `comando: ninguno` if the project has no automated tests) and append it to the end of the `context:` using surgical editing, keeping in mind the 40KB limit.
   - Show the timeout with its unit in the question (e.g. `timeout: 5 min`).
   - Write `## Tests` with this exact format (each key is a list item `- key: value`, indented inside `context: |`; the unit of `timeout` is NOT written in the file):
     ```yaml
     context: |
       <existing text>

       ## Tests
       - comando: python -m pytest -q
       - timeout: 5
     ```
   - Write only the keys the user declares: omit `comando-rapido`, `entorno` and `excluir` when not declared — never write filler values such as "no declarado" or "ninguno".
   - If the user does not know how tests run: infer `comando` from the repo when it is evident (pytest with `test_*.py` files, `scripts.test` in `package.json`, etc.), write it together with `- timeout: 5` as the default (`timeout` is mandatory whenever there is a command), and mention both in the final summary as inferred. If it cannot be inferred, do NOT write `## Tests` (not even `comando: ninguno`), mark the command as pending in the Test Plan, and ask again in the next propose.

   Read the `## Arquitectura` subsection from the `context:` in `openspec/config.yaml`. If it does not exist, ask the user for it ONCE (in the same question as `project_type` and `## Tests` if they are also missing). Build an inferred proposal combining top-level folders of the repo and `src/` (excluding implicit folders and `node_modules/`) with the suggested row for the `project_type` from the global `CLAUDE.md`. Present the options: "Usar la inferida", "Usar la sugerida para <tipo>", or custom. If the user answers "no sé", write the inferred proposal with `- estado: inferido — revisar` and mention it in the final summary. Append `## Arquitectura` to the end of `context:` using surgical editing, keeping in mind the 40KB limit.
   - When writing `## Arquitectura` for the first time: if the repo has no code files (extensions: `.py`, `.ts`, `.tsx`, `.js`, `.jsx`, `.mjs`, `.cjs`, `.vue`, `.svelte`, `.ps1`, `.psm1`, `.cs`, `.java`, `.go`, `.rb`, `.php`, `.sql`) outside implicit folders, append `- tamaño: 500, 1000`. In a repo that already has code, do NOT add `tamaño` unless the user approves an architecture recommendation or explicitly requests it.
   - Write `## Arquitectura` with this format (each folder is a list item `- <path>/: <description> | no importa: <path>/`, indented inside `context: |`):
     ```yaml
     context: |
       <existing text>

       ## Arquitectura
       - src/app/: rutas y páginas; compone frontend y backend
       - src/backend/: Payload, DB, secretos, integraciones
       - src/frontend/: componentes, estilos, hooks de cliente | no importa: src/backend/
       - tests/: espejo de src/
     ```
   - Optional keys without trailing slash: `comando` and `timeout` (in minutes, mandatory if `comando` is declared), `estado: inferido — revisar`, `nivel` (`0`, `1-nucleo-funcional`, `2-capas`, `2-tuberias`, `3-hexagonal`, `3-modular`), `tamaño` (`<aviso>, <advertencia>` in lines), and `tamaño-excluir` (comma-separated paths with trailing slash).
   - Folders always allowed implicitly without declaration: root files, `openspec/`, `docs/`, dotfolders (`.*`), and subfolders of any declared folder.
   - Check if `nivel` is declared in `## Arquitectura`: if `## Arquitectura` is present, check whether `nivel` is declared and if its value matches a recipe (`0`, `1-nucleo-funcional`, `2-capas`, `2-tuberias`, `3-hexagonal`, `3-modular`). Record the result for the final summary. If `nivel` is missing or invalid, the propose flow does not block (el propose no se bloquea y continúa con todos sus artefactos) and do not correct the value on your own (no corregir el valor por su cuenta).
   - Check if `## Alcance`, `## Datos`, `## Stack`, or `## Calidad` exist in `context:` of `openspec/config.yaml`. If any are missing, do NOT ask the user during propose; record which ones are missing to include a notice in the final summary.

1. **If no clear input provided, ask what they want to build**

   Use the **AskUserQuestion tool** (open-ended, no preset options) to ask:
   > "What change do you want to work on? Describe what you want to build or fix."

   From their description, derive a kebab-case name (e.g., "add user authentication" → `add-user-auth`).

   **IMPORTANT**: Do NOT proceed without understanding what the user wants to build.

2. **Create the change directory**
   ```bash
   openspec new change "<name>"
   ```
   This creates a scaffolded change in the planning home resolved by the CLI with `.openspec.yaml`.

3. **Get the artifact build order**
   ```bash
   openspec status --change "<name>" --json
   ```
   Parse the JSON to get:
   - `applyRequires`: array of artifact IDs needed before implementation (e.g., `["tasks"]`)
   - `artifacts`: list of all artifacts with their status and dependencies
   - `planningHome`, `changeRoot`, `artifactPaths`, and `actionContext`: path and scope context. Use these instead of assuming repo-local paths.

4. **Create artifacts in sequence until apply-ready**

   Use the **TodoWrite tool** to track progress through the artifacts.

   Loop through artifacts in dependency order (artifacts with no pending dependencies first):

   a. **For each artifact that is `ready` (dependencies satisfied)**:
      - Get instructions:
        ```bash
        openspec instructions <artifact-id> --change "<name>" --json
        ```
      - The instructions JSON includes:
        - `context`: Project background (constraints for you - do NOT include in output)
        - `rules`: Artifact-specific rules (constraints for you - do NOT include in output)
        - `template`: The structure to use for your output file
        - `instruction`: Schema-specific guidance for this artifact type
        - `resolvedOutputPath`: Resolved path or pattern to write the artifact
        - `dependencies`: Completed artifacts to read for context
      - Read any completed dependency files for context - always re-read them from disk, even if you saw them earlier in the conversation (the user may have edited them)
      - **Inspect the relevant project before drafting**: Read `context` and `rules` first, then inspect relevant implementation, nearby tests, configuration, and documentation outside `openspec/`. Keep inspection read-only and proportional to the change; reuse findings for later artifacts and inspect more only as needed.
        - Identify the target project from the request and project context; the planning home may be separate from the code. If the target is unclear, ask. For greenfield or non-code changes, inspect the available structure and relevant documents. If source is unavailable, state the limitation and ask when it materially affects the plan.
        - Ground scope, approach, and tasks in what you find. Distinguish observed behavior from assumptions and proposed additions; surface conflicts with existing specs instead of silently deciding which is correct.
        - Do this discovery now, rather than leaving generic "explore the codebase" or "make a plan" tasks for implementation. Keep any necessary follow-up investigation specific to an unresolved question.
      - Create the artifact file using `template` as the structure and write it to `resolvedOutputPath`
      - Apply `context` and `rules` as constraints - but do NOT copy them into the file
      - Show brief progress: "Created <artifact-id>"

   b. **Continue until all `applyRequires` artifacts are complete**
      - After creating each artifact, re-run `openspec status --change "<name>" --json`
      - Check if every artifact ID in `applyRequires` has `status: "done"` in the artifacts array
      - Stop when all `applyRequires` artifacts are done

   c. **If an artifact requires user input** (unclear context):
      - Use **AskUserQuestion tool** to clarify
      - Then continue with creation

5. **Show final status**
   ```bash
   openspec status --change "<name>"
   ```
   Also run `openspec validate "<name>"` and fix any error before continuing.

6. **Write to the Obsidian vault**

   If `$vault` does not exist: skip silently and note it in the output. Never block the propose flow on the vault.

   Otherwise, use the Write tool (create the folders if missing) for:

   a. **Decisions note** at `$vault\projects\$p\decisions\YYYY-MM-DD-<name>.md`, with frontmatter (`project`, `change`, `date`, `status: activo`, `tags: [openspec, proposal]`) and sections `## Qué se propone` (summary of proposal.md), `## Decisiones de diseño` (key points of design.md) and `## Links` (`[[<project>/context]]`).

   b. **context.md** at `$vault\projects\$p\context.md`: read the existing file first and rewrite it in the standard format (frontmatter `project` + `updated`; sections `## Estado actual`, `## Último change`, `## Decisiones recientes`, `## Contexto activo`). Keep the last 2-3 relevant decisions already there and add this change's. Set `Estado actual` to the active change and `Contexto activo` to: "Change listo para implementar. Ejecutar en el Agente: /openspec-apply-change <name> (Antigravity) o /opsx-apply <name> (Cursor)". Do NOT discard existing useful context.

   c. **Vault sync**: `git -C $vault add -A`, commit `chore: <project> — propose <name>` and push. If the push fails (no network, no remote, wrong GitHub account), continue and warn at the end.

   Show: `Obsidian: $vault\projects\<project>\decisions\YYYY-MM-DD-<name>.md`

7. **Create the branch and commit the artifacts**

   ```bash
   git checkout -b change/<name>
   ```

   Then commit the change artifacts (spec changes go in their own commit, per the global rules), including `openspec/config.yaml` when modified by this propose:
   ```bash
   git add openspec/changes/<name>
   git add openspec/config.yaml   # only if modified by propose
   git commit -m "docs: propose <name>" -m "Spec-ID: <name>"
   ```
   Run `git diff --staged` first and make sure nothing sensitive is staged. Do NOT push.

**Output**

After completing all artifacts, summarize:
- Change name and location
- List of artifacts created with brief descriptions
- Obsidian note path (or skip notice)
- Branch created: `change/<name>` and artifacts commit
- Missing project profile notice (if applicable, including missing `## Calidad`): "Falta la ficha del proyecto (`<lo que falta>`): corré `/ficha`"
- Architecture suggestion (D1): If `## Arquitectura` is present in `openspec/config.yaml` but lacks `nivel` or declares a value that does not match any recipe: include `Sugerencia: corré `/arquitectura` para evaluar la arquitectura del proyecto (<motivo>)` with motivo "`## Arquitectura` no declara `nivel`" or "`nivel: <valor>` no corresponde a ninguna receta" (no corrige el valor por su cuenta). If `nivel` is declared with a valid recipe, or if an architecture recommendation was applied in this same change (writing `nivel`), do not suggest (no sugiere). Show at most once per propose.
- What's ready: "All artifacts created! Ready for implementation."
- Prompt: "Ejecutá en el Agente: `/openspec-apply-change <name>` (Antigravity) o `/opsx-apply <name>` (Cursor)"
- "Cuando el Agente termine: `/opsx:verify <name>`"

**Artifact Creation Guidelines**

- Follow the `instruction` field from `openspec instructions` for each artifact type
- The schema defines what each artifact should contain - follow it
- Read dependency artifacts for context before creating new ones
- Use `template` as the structure for your output file - fill in its sections
- For `proposal.md`: scope check against `## Alcance`:
  - When drafting `proposal.md`, compare what the change requests against each `- no incluye:` item in `## Alcance`, evaluating by semantic meaning rather than literal match.
  - If a match is found, ask the user ONCE using `AskUserQuestion` with three options:
    - "Seguir y pasarlo al alcance": update that line to `- incluye:` in `openspec/config.yaml` using surgical editing (under 40 KB), and include `openspec/config.yaml` in the artifacts commit.
    - "Seguir sin tocar el alcance": keep `## Alcance` unchanged and document in `## Non-goals` or `## Impact` of `proposal.md` that the change requests something marked as not included in the version.
    - "Cancelar": abort proposal creation (remove the change directory if created with `openspec new change`) and stop.
- For delta specs (`specs/**/*.md`): invalid data scenarios for external data:
  - When drafting delta specs, identify requirements that touch an external data source: their text or scenarios read, receive, validate, or store data declared in `## Datos` with `(externo)`, or any of its fields.
  - To each of these requirements, add at least one scenario at the end named `Dato inválido: <caso>`, choosing cases appropriate for the field: empty or missing, malformed (e.g., phone with letters or email without `@`), duplicate, or out of range (dates or amounts).
  - The THEN clause must state what the system does: discard the row, warn, return an error, or record without personal data.
  - Each invalid data scenario must have its corresponding row in the `## Test Plan` (`auto` if the project has tests).
  - If the project does not declare `## Datos`, this step does not apply.
- For `design.md`: system impact review in `## Impacto en el sistema`:
  - Include `## Impacto en el sistema` before `## Ubicación de archivos` (and before `## Recomendación de arquitectura` if present), with four bold subsections:
    - **Componentes afectados:** modules, integrations, data, or other projects outside the files modified by the change. If none, write "ninguno fuera del change".
    - **Atributos de calidad:** evaluation of quality attributes declared in `## Calidad` (`rendimiento`, `disponibilidad`, `escalabilidad`, `costo`, `mantenibilidad`). For each attribute with priority `alta`, write a line with its impact ("sin efecto" is valid) and, if affected, `— Verificación: <cómo>` using `Sxx`, `revisión del diff: <qué se busca>`, or `manual: <pasos>`. Mention medium or low priority attributes only if the change affects them. If `## Calidad` is not declared in `openspec/config.yaml`, write "sin `## Calidad` declarada" and include a notice in the final summary suggesting `/ficha`.
    - **Decisiones de arquitectura:** "ADR nuevo: NNNN", "Reemplaza a: NNNN", or "ninguna".
    - **Deuda técnica:** technical debt that the change adds, pays, or discovers ("agrega: …", "paga: …", "descubre: …"), or "ninguna".
  - Complete this section by inspecting the touched code and its usages, `docs/arquitectura/vision.md` if it exists, and the vault architecture summary. No code, credentials, or personal data are copied.
- For `design.md`: Architecture Decision Records in `## ADR`:
  - When the change makes a decision that outlives it according to the closed criteria:
    1. chooses or changes a technology in `## Stack`;
    2. changes the `nivel` in `## Arquitectura` (including "Aplicar en este change" from a recommendation);
    3. adds or changes an external integration;
    4. adopts a cross-cutting pattern (error handling, logging, authentication, data access);
    5. resolves a trade-off between two quality attributes.
    If none of these criteria apply, do NOT include `## ADR`.
  - When applicable, include a `## ADR` section in `design.md` with the full text of the ADR inside a `markdown` code block:
    - Heading `# NNNN. <título>` (NNNN is the next number after the highest in `docs/adr/`, or `0001`; slug in kebab-case).
    - Metadata: `Estado: aceptada`, `Fecha: AAAA-MM-DD`, `Change: <nombre>`, and `Reemplaza a: NNNN` (only if replacing a previous ADR).
    - Sections: `## Contexto`, `## Alternativas` (each with why it was discarded), `## Decisión`, and `## Consecuencias` (positive and negative).
  - Claude does NOT write the ADR file in the repository: the repository file is created by the Agent with a task in `tasks.md` to copy the content of the `markdown` code block ("Crear `docs/adr/NNNN-<slug>.md` con el contenido del bloque de código de `## ADR` del design", and if replacing an earlier ADR, "Cambiar `Estado:` de `docs/adr/<anterior>` a `reemplazada por NNNN`"). No code, credentials, or personal data are copied into the ADR.
- For `design.md`: initial vision and vision updates in `## Visión inicial`:
  - Every project maintains a living document `docs/arquitectura/vision.md` with:
    - `## Propósito`: one or two lines referencing description and business goals in `openspec/config.yaml` (do not copy them).
    - `## Contexto e integraciones`: actors and external systems the project interacts with (Mermaid diagram optional).
    - `## Componentes`: each declared folder in `## Arquitectura` with its specific responsibilities in more detail than `config.yaml`.
    - `## Decisiones vigentes`: list of accepted ADRs `- [NNNN. <título>](../adr/NNNN-<slug>.md)`.
    - `## Hoja de ruta`: prioritized technical debt `- [alta|media|baja] <deuda> — origen: <change o ADR> — propuesta: <cómo pagarla>`.
  - If `docs/arquitectura/vision.md` does not exist: include `## Visión inicial` in `design.md` with initial content inferred from the repo, project profile, and existing ADRs. `tasks.md` MUST include a task for the Agent to create `docs/arquitectura/vision.md` with this content.
  - If `docs/arquitectura/vision.md` already exists and `## Impacto en el sistema` names a new ADR, new components, or debt added or paid: `tasks.md` MUST include a task for the Agent to update `docs/arquitectura/vision.md` specifying which lines change.
  - Claude does NOT write or edit the vision file in the repository: the repository file is created or updated by the Agent with a task, and no code, credentials, or personal data are copied.
- For `design.md`: architecture signals detection and recommendation:
  - As part of project inspection, read `~/.claude/skills/arquitectura/references/recetas.md` and check existing code files that the change will modify or enlarge, looking for the **Señales** of the recipe of the level following the one declared (if no `nivel`, check level 1 and the level 2 recipes matching `project_type`). For the size signal, use the declared `tamaño` thresholds, or 500 and 1000 if not declared (only for recommending; verify does not measure without `tamaño`). Before counting a signal, check **Cuándo no aplicarla** for that recipe: if it applies (for example, a script of less than ~150 lines), the signal is discarded and generates no recommendation; it may be mentioned as an observation in the final summary, not in the design. If recipes are not installed, skip this step and warn in the final summary.
  - If at least one signal is found, add the `## Recomendación de arquitectura` section before `## Ubicación de archivos` with these bold subsections: **Qué vi** (concrete files, lines, and functions), **Qué problema trae**, **Qué propongo** (level, folders, and rules from the recipe adapted to the repo), **Cuánto cuesta** (files to move and whether it can be done in stages), **Qué descarté** (alternative recipes or doing nothing, with rationale), **Pautas para el Agente** (guidelines from the recipe), and **Decisión**. Without signals, do NOT include this section.
  - When a recommendation is generated, ask the user ONCE using `AskUserQuestion` with three options: "Aplicar en este change", "Aplicar en un change aparte", and "No aplicar todavía". Record the answer in **Decisión**:
    - "Aplicar en este change": update `## Arquitectura` in `openspec/config.yaml` with `nivel`, folders, and rules (and `tamaño: 500, 1000` if not present) using surgical editing (under 40 KB). `tasks.md` must include tasks to move the code, preceded by characterization tests (`Cxx`).
    - "Aplicar en un change aparte": do NOT modify `## Arquitectura`; the final summary suggests `/issue-creation` for the refactoring change.
    - "No aplicar todavía": do NOT modify `## Arquitectura`.
- For `design.md`: include a `## Ubicación de archivos` section before `## Security Layer` with a table `Archivo nuevo | Carpeta declarada`. If a new folder is needed that is not declared in `## Arquitectura`, justify it there, and `tasks.md` MUST include a task to add it to `## Arquitectura`.
- For `design.md`: personal data controls in `## Security Layer`:
  - If `## Datos` declares any entry with `| personal` and the change reads, stores, displays, or transmits that data, include a "Datos personales" subsection in `## Security Layer`.
  - State how each applicable control is met:
    - Do not log personal data (in application logs, errors, or console outputs).
    - Request and store only necessary fields.
    - Mask in reports, screenshots, and non-production outputs (e.g., `261-***-**34`).
    - Do not use real data in tests or fixtures (use invented data).
    - Do not expose in URLs or query parameters.
- For `design.md`: verification of each control in `## Security Layer`:
  - Every applicable control in `## Security Layer` MUST terminate with `— Verificación: <cómo>`, where `<cómo>` is one of:
    - `Sxx` (Test Plan scenario);
    - `revisión del diff: <qué se busca>`;
    - `manual: <pasos>`.
    Example: `No loguear datos personales — Verificación: revisión del diff: ningún print ni log con campos de leads`.
- For `design.md`: generate a `## Test Plan` section before `## Open Questions` with the header (command, whether to force the suite and why), the scenario table `ID | Requirement / Escenario | Verificación | Archivo previsto` with IDs `S01`... (one row per delta specs scenario; `auto` or `manual: <reason>` with steps), and the characterization table `ID | Archivo existente | Qué fija | Cambio intencional` with IDs `C01`... when the change modifies existing code. If the change intentionally modifies existing behavior, either the `Cxx` fixes the current behavior and says how it changes (the task updates that test), or the `Cxx` leaves that part out and says so in "Cambio intencional", naming the `Sxx` that covers the new behavior; no modified existing behavior may be left without a `Cxx` or `Sxx`. Specify that each automated test must carry the marker `test-plan: <change-name>/<ID>` in name, comment, or docstring.
- For `tasks.md`: group test tasks before implementation tasks (first `Cxx`, "write and run green before modifying <file>", then `Sxx`). Each test task must mention its IDs and command. Add a task for each `manual` ID with its steps. If the project declares a test command but has no test infrastructure yet, add an initial task to set it up, and mention this in the Impact section of `proposal.md`.
- **IMPORTANT**: `context` and `rules` are constraints for YOU, not content for the file
  - Do NOT copy `<context>`, `<rules>`, `<project_context>` blocks into the artifact
  - These guide what you write, but should never appear in the output

**Guardrails**
- Create ALL artifacts needed for implementation (as defined by schema's `apply.requires`)
- Always read dependency artifacts before creating a new one
- If context is critically unclear, ask the user - but prefer making reasonable decisions to keep momentum
- If a change with that name already exists, ask if user wants to continue it or create a new one
- Verify each artifact file exists after writing before proceeding to next
- NEVER write production code — Claude is the architect, the Agent implements
- Vault write: if the vault doesn't exist or the push fails, don't block the propose flow
- Branch creation: always create `change/<name>` after artifacts are ready; never work on main/master for a change with spec
